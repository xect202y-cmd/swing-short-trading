# 스윙 로직 정교화 — 검증 하니스 + 4레버 이터레이션 (설계)

- 작성일: 2026-06-30
- 상태: 설계 승인됨 (구현계획 대기)
- 대상 repo: `swing-short-trading` (페이퍼 트레이딩, 시드 500만)

## 1. 목표와 비목표

**북극성(동기부여용, 최적화 타깃 아님):** 일평균 +1%.

**실측·관리 목표 밴드:** 일 **+0.1~0.15%** / 연환산 **+20~40%** (역사상 최고 퀀트펀드 상단~그 이상, "안 터지면서 도달 가능한 최대치").

**핵심 원칙:** 수익률 자체를 "맞추는" 게 아니라 **엣지를 실제로 끌어올리고, 그게 진짜인지 아웃오브샘플로 검증**한다. 1%/일을 하드 타깃으로 두면 과최적화·과레버리지로 계좌가 터지므로 절대 최적화 목적함수로 쓰지 않는다.

**비목표:** 레버리지·파생·실전 주문 전환(페이퍼 유지). 그리드 전역 최적화(커브핏 유발).

## 2. 접근법 — A: 순차 검증 이터레이션

4개 레버(유니버스·청산·진입·사이징)를 **모두** 다루되, **한 번에 하나씩** 바꿔 아웃오브샘플 A/B로 검증한다. 이기면 확정, 지면 폐기. 동시 변경(전역 최적화)은 무엇이 효과였는지 분리 불가 + 노이즈 다중 커브핏이라 배제.

전제: 어떤 레버든 손대기 전에 **1단계 검증 하니스(Phase 0)**를 먼저 깐다. 현재 표본(미국 6종목·120일·36거래)으로는 개선과 운이 구분되지 않는다.

## 3. Phase 0 — 검증 하니스 (기반)

현재 백테스트의 3대 결함을 메운다: ① 표본 6종목·120일 ② 승률만 측정 ③ 인샘플=아웃샘플(과최적화 무방비).

### 3.1 데이터 확장
- **유니버스:** 관심종목 전체(KR+US, 티커 있는 노트 전부). 지금 6 → 수십 종목.
- **히스토리:** 백테스트 전용 `backtest.lookback_days`(기본 ~500거래일, 약 2년)로 별도 fetch. 라이브 지표용 `market_data.lookback_days`(120)와 분리.

### 3.2 지표 — `BacktestReport`로 확장
승률뿐 아니라:
- **기대값**(거래당 평균 %, 비용 차감 후 — 현 `avg_return` 재사용)
- **손익비**(avg win / avg loss), **Profit Factor**
- **최대낙폭(MDD)**, **Sharpe**, **연환산 거래수**, 노출(exposure)

전 종목 거래를 **시간순 풀링**해 flat-bet 자산곡선 1개를 구성 → MDD·Sharpe 산출. (Phase 4 사이징 전까지는 동일 베팅 가정.)

### 3.3 아웃오브샘플 검증 (핵심)
- 히스토리를 **인샘플(앞 70%) / 아웃샘플(뒤 30% 홀드아웃)**으로 분할.
- 두 구간 지표를 나란히 출력 → IS는 좋은데 OOS에서 무너지면 **과최적화 적발**.
- (스트레치) 워크포워드: 창을 굴려가며 반복 검증.

### 3.4 A/B 비교기 + 가드레일
- `baseline 파라미터 vs candidate 파라미터`를 **같은 OOS 데이터**에 돌려 나란히 비교 → 판정 **✅개선 / ➖무의미 / ❌악화**.
- **표본 가드:** OOS 거래 < 100건이면 "표본부족, 판정보류" 경고.
- 결과 → 옵시디언 리포트(`04_Trading/Backtests/`) + 디스코드 요약. 기존 `logic_version` A/B 배관 재사용.

### 3.5 구현 위치
- `strategy/backtest.py`: 지표·자산곡선·OOS 분할 추가.
- `strategy/harness.py`(신설, 얇게): baseline vs candidate 비교·판정.
- `config.yaml`: `backtest:` 섹션 추가(`lookback_days`, `oos_fraction`, `min_oos_trades`, `universe`).
- CLI: `swing-trader harness` 신설 또는 기존 `backtest` 확장.

## 4. Phase 1~4 — 레버 이터레이션 루프

각 레버 공통 루프:
1. 변경을 파라미터/규칙 변이로 정의
2. baseline vs candidate → 하니스 OOS A/B
3. 판정 + 표본가드
4. ✅개선 & OOS 유지 → 확정(logic 버전업·changelog·config 반영) / ❌·➖ → 폐기 + 사유 기록
5. 새 baseline로 갱신 → 다음 레버

### Phase 1 · 유니버스 (표본 확보 겸용)
관심종목 전체 확장 + 유동성/데이터길이 필터. A/B: 전체 vs 필터링. 목적 = 기회 수·분산 확보.

### Phase 2 · 청산 (기대값 최대 레버)
기존 config 노브 변이: `runner on/off`, `take1_pct`, `default_stop_pct`, `trail_pct`, `partial_exit_pct`, `momentum_exit_days`. **원칙 있는 변이만, 레버당 ≤5개**(커브핏 최다 구간).

### Phase 3 · 진입 품질
현재 진입(20일선 눌림+반등+거래대금)에 필터 추가: 추세(가격>60일선·정배열) / RS(지수 대비 상대강도) / 거래량 급증 / 매매기법 패턴 부합.
- 선행 소작업: 백테스트 진입조건이 현재 하드코딩 → **진입 규칙 plug-in 파라미터화**.
- A/B: 베이스 vs +필터(개별).

### Phase 4 · 사이징
flat-bet → **변동성 타겟(size ∝ 1/ATR)** 또는 **하프-켈리**(측정 엣지 기반). 하니스 자산곡선을 가변 베팅 지원하도록 확장. A/B: MDD·Sharpe·CAGR로 비교.

## 5. 가로지르는 가드레일
- **과최적화 예산:** 레버당 변이 ≤5, 단순·강건 우선, **OOS 개선만 인정**(IS 개선 불충분).
- **라이브 = 최종 검증:** 500만 페이퍼 계좌의 전진성과를 백테스트 기대값과 대조. 백테는 좋은데 라이브가 안 따라오면 기각.
- **1%/일은 대시보드 지표일 뿐**, 최적화 목적함수로 쓰지 않음.

## 6. 성공 기준
- 각 확정 변경: OOS에서 baseline 대비 **기대값 또는 Sharpe 개선** + 표본가드 통과.
- 4레버 종료 시: OOS 기준 **기대값/Sharpe/MDD가 baseline보다 명확히 개선**된 로직 vN + 옵시디언에 전 과정(변이·판정·사유) 기록.

## 7. 기존 코드 접점 (따를 패턴)
- `strategy/backtest.py::simulate(...)` — 이미 `take_pct/stop_pct/runner/take2_pct/trail_pct` 파라미터화됨. 여기에 지표·OOS 확장.
- `strategy/logic_version.py` — config 평탄 스냅샷·diff·버전 저장. 확정 변경 기록에 재사용.
- `review/analytics.py::compute_metrics` — profit_factor·max_drawdown 로직 존재(라이브 계좌용). 하니스 지표 산식 참고/공유.
- `main.py::run_logic / run_backtest` — A/B·기록 배관. 하니스 오케스트레이션이 재사용.
- `notify/health.py` — 데이터 수집 실패 경고(이미 구축). 하니스도 실데이터 비율 점검에 사용.

## 8. 미해결/주의
- `backtest.render_md`의 규칙 설명이 "최대 5거래일"로 표기되나 실제 `max_hold_days=20` — 표기 불일치, 하니스 작업 시 실제값과 일치시킴.
- 2년 히스토리 fetch는 pykrx/yfinance 호출량↑ → 캐시/레이트리밋 고려.
- KR·US 혼합 풀링 시 환율·거래시간대 차이가 자산곡선에 미치는 영향(이미 KRW 환산은 됨) 점검.
